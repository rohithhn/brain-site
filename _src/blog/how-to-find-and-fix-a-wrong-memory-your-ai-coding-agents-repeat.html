What is a wrong memory, and how do you fix one?

A wrong memory is a stored decision, fact or lesson that no longer matches your codebase, and that every connected AI coding agent keeps reading as if it were true. How to find and fix a wrong memory your AI coding agents keep repeating takes four steps: search the shared memory for the bad entry, see which tools and projects it came from, edit or delete it, then confirm the corrected version shows up in Claude Code, Codex and Cursor.

Stale memory, outdated memory and incorrect AI agent memory all describe the same failure. It is rarely a model bug. Someone said "use Redis for sessions" three weeks ago, the team later dropped Redis, and the memory still says Redis. Now three tools suggest it in three different ways.

The fix is a few minutes in the Memory view, provided your memory sits in one place. If it is scattered across CLAUDE.md, AGENTS.md and Cursor rules, you are editing three files by hand and hoping they agree. Our post on using multiple AI coding agents without losing context covers why that drifts.

Why do agents keep repeating the same wrong answer?

Because memory is read at the start of a session, not re-checked against the code, so a wrong entry gets injected every time until someone changes it.

A memory layer captures, extracts, stores, retrieves and injects. Nothing in that loop asks whether an entry is still true. If the entry is a decision, it reads as an instruction. If it came from a drafted lesson, it may have been inferred from a single bug fix and generalised too far.

One shared memory makes this worse in one way and better in another. A bad entry now reaches every tool, which is why the repeated suggestions feel inescapable. But there is also exactly one place to correct it. The background on how this loop works is in why your AI coding tools forget everything.

How do you find the wrong memory in the Memory view?

Open the Memory view on localhost, search for a keyword from the bad suggestion, and filter by project or tool until only the suspect entries remain.

The Memory view is the web interface that runs on your own machine. It lists every memory from every tool and every project in one place, with a search box across all of it. You can also filter down to a single project, such as api, web or infra.

Search for the noun the agent keeps repeating, not for the whole sentence. If Cursor keeps importing Redis, search "redis". Expect several hits of different kinds: a decision, a bugfix note and perhaps a learning. Each entry is labelled by type, so you can tell a decision someone made from a lesson the system drafted.

How do you see which tools picked it up?

Filter the same search to one tool at a time and compare the results; an entry that appears under Claude Code, Codex and Cursor has already spread.

Five tools can read and write this memory: Claude Code, Codex, Cursor, Antigravity and Kilo Code (Kilo Code is in beta). Run the search once per tool you use. You are looking for the origin, the first entry that stated the bad decision, because that is the one to correct. Later entries are usually echoes: a commit note, a health check, a second mention.

If the origin is a decision, fix that first. If the origin is a draft learning you never approved, you have a different problem, and we come back to it below.

How to find and fix a wrong memory your AI coding agents keep repeating: a worked example

Search the term, list the matches, correct the origin, delete the echoes, and pin the corrected decision so every session sees it.

This is an illustrative example, not a benchmark. A team dropped Redis for sessions and moved to SQLite. Redis stayed only for the old job queue. Agents kept suggesting Redis session code anyway. Searching "redis" in the Memory view returned 3 entries, and 2 of them were stale:

EntryTypeStatusAction
Sessions are stored in RedisDecisionStale (the origin)Edit
Added Redis health check to deploy.shBugfixStale (an echo)Delete
Redis only serves the job queueLearningCorrectKeep

The decision gets edited to read "Sessions live in SQLite; Redis only served the old job queue." The health-check note is deleted. The corrected decision is then pinned, which means every session sees it, whatever the task. Three entries, two actions, one pin.

Should you edit or delete a wrong memory?

Edit when the topic still matters and the facts changed; delete when the entry should never have existed.

I lean toward editing. A deleted decision leaves a gap, and the next session may invent the same wrong answer from scratch. A corrected decision states what is true now and often records why the old one was dropped, which is the part agents actually need.

Delete the noise: duplicates, one-off bugfix notes about code that is gone, lessons that were wrong from the start. Deletes can be undone, so the cost of a mistaken delete is low. Use restore if you remove the wrong row.

How do you check the fix reached Claude Code, Codex and Cursor?

Open a fresh session in each tool, ask the question that used to produce the wrong answer, and read the briefing the tool was given.

Do not trust the edit until you have seen it land. For Claude Code, the briefing is written into CLAUDE.md at roughly 2,000 tokens, so open that file and look for the corrected line. For Codex and Cursor, start a new session and ask the same thing: "How do we store sessions?" If any tool still answers Redis, check that its connection is active and that you started a new session rather than resuming an old one. An old session keeps whatever context it already loaded.

$ grep -n -i "redis" CLAUDE.md # expect: the corrected SQLite decision, not "sessions in Redis"

Because there is one memory and not three copies, a single correct entry is all each tool needs. If you want the plumbing, how an MCP memory server connects to your tools explains how they read it.

How do you stop agents from inferring bad lessons?

Review drafted learnings before they become memory: approve the ones that generalise correctly, dismiss the ones that don't.

The system drafts lessons from problems it sees, such as "When a cache layer is removed, also remove its health checks and env vars." Drafts sit in the Memory view marked as drafts, with Approve and Dismiss buttons. That step is your quality gate. A lesson inferred from one project can be wrong for another, so dismiss anything that reads as broader than the evidence.

You can also rate approved learnings as helpful or not helpful. A short weekly pass over drafts and anything rated unhelpful keeps incorrect AI agent memory from building up. At Open Agentic Brain and Memory, we keep that review in your hands on purpose, because only you know which decisions are still current. The story of the brain shows the full Memory view with these controls.

Where does this data live while you edit it?

On your machine: the memory is a local SQLite database, memory.db, served to you on localhost, with no account and no server of ours.

When you search or edit, you are working against that local file. Backups are a compact snapshot, encrypted with age, with the key held only in your OS Keychain. The snapshot goes to a release asset on your own private GitHub repo, and your other machines restore from it. Whether edits propagate to a second laptop depends on that restore, so after a big cleanup, take a fresh snapshot. FAQ

Can an agent re-create a memory I deleted?

Yes, if the same decision is stated again in a later session, it can be captured again. Correcting and pinning the right version works better than a bare delete, because it gives agents the true answer to find first.

Should I edit or delete a wrong memory?

Edit it when the topic is still relevant and only the facts changed. Delete it when it is a duplicate, an echo of a removed feature, or was never correct. Deletes can be undone, so a mistake costs little.

Does deleting a memory affect past sessions?

No. It changes what future sessions are told, not what an earlier conversation already read. Start a new session in each tool to see the corrected memory.

How do I stop agents from inferring bad lessons?

Review drafted learnings in the Memory view and dismiss any that overgeneralise from one project or one bug. Approved lessons can be marked not helpful later if they turn out to mislead.

Is my memory data sent anywhere?

There is no account and no server of ours. Memory is stored locally in memory.db. Optional backups are age-encrypted, with the key kept in your OS Keychain, and go only to your own private GitHub repo.
